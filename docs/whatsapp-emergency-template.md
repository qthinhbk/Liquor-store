# WhatsApp emergency alert template

## Status and scope

This document records the approved owner-facing WhatsApp template used by the Cloud API adapter.

- The revised `emergency_security_alert` template is active in the test WhatsApp Business Account as a Meta-approved `UTILITY` template in English as of August 29, 2026.
- Version 2 uses a VIDEO header, four body parameters, the `Ketch Enterprise AI` footer and a `View alert` URL button that opens the exact dashboard alert.
- Version 2 is the default and the required operational choice for new endpoint configuration. Version 1 remains accepted by the sender during the compatibility window so immutable historical delivery snapshots can still be delivered.
- The Cloud API adapter is implemented. It supplies a fresh short-lived HTTPS evidence URL to the video header for each send attempt and fails closed if a usable video URL is unavailable.
- No unsigned dashboard URL, object-storage key or provider credential is placed in the template.

## Meta template definition

| Meta field | Value |
| --- | --- |
| Name | `emergency_security_alert` |
| Internal version | `whatsapp-emergency-security-alert-v2` |
| Category | `UTILITY` |
| Language | `en` |
| Header type | Video |
| Header sample | An emergency evidence clip submitted only for Meta review |
| Footer | `Ketch Enterprise AI` |
| Button | URL button labelled `View alert` |
| Button URL | `https://ketchenterprise.net/#/alerts?alertId={{1}}` |

### Body

```text
A potential emergency was detected at {{1}}.

Camera: {{2}}
Detected: {{3}}
Event: {{4}}

Open this alert using the button below and follow your store's emergency procedure. This automated alert does not contact emergency services.
```

The copy deliberately says `potential emergency`. It must not claim that a weapon, theft or other crime definitely occurred, and it must not imply that the system contacted law enforcement.

### Parameter contract and Meta sample values

| Position | Payload source | Required rendering rule | Sample submitted to Meta |
| --- | --- | --- | --- |
| `{{1}}` | `store.name` | Owner-visible store name | `Liquor Store` |
| `{{2}}` | `camera.name` | Owner-visible camera name; fallback `Unknown camera` | `Whole store` |
| `{{3}}` | `alert.detectedAt` + `store.timezone` | Format once in the store timezone and include the timezone abbreviation | `Aug 24, 2026, 9:42 PM CDT` |
| `{{4}}` | Owner-safe alert type label | For the initial rule use `Possible violence or weapon detected` | `Possible violence or weapon detected` |

Render parameters as plain text. Strip control characters and collapse unexpected line breaks before calling Meta. Do not render AI confidence, raw metadata, person identity, RTSP URLs, camera credentials, object-storage keys or provider secrets.

The VIDEO header is a separate template component and does not change the body parameter order. For an alert delivery, its media link comes only from the in-memory `RenderPayload.ReviewURL` generated by the secure review service. For an explicit TEST delivery, `config.testVideoUrl` may provide a public HTTPS sample clip. Private, local, credential-bearing or non-HTTPS URLs are rejected before the provider call.

## Emergency-only behavior

The initial notification rule remains `minimumSeverity = CRITICAL`, `alertTypes = ['WEAPON_DETECTED']` and `cooldownSeconds = 0`.

- Suspicious-behavior alerts stay in the dashboard and do not use this template.
- Emergency notifications do not expose `Match` or `False alarm` actions in WhatsApp.
- The owner reviews the evidence and follows the store procedure; the system never contacts police automatically.
- Every independent emergency gets its own delivery. Existing `dedupeKey` semantics prevent only duplicate enqueue for the same incident.

## Endpoint configuration contract

For a WhatsApp `notification_endpoints` row:

| Field | Meaning |
| --- | --- |
| `providerAccountRef` | Meta Phone Number ID used to send the message. |
| `destinationRef` | Opted-in owner phone number in E.164 format. Treat it as personal data and mask it in API responses and logs. |
| `credentialRef` | Runtime secret reference such as `env://WHATSAPP_ACCESS_TOKEN`; never the token itself. `render-secret://` remains fail-closed until a deployment resolver is implemented. |
| `config.wabaId` | Non-secret WhatsApp Business Account ID. |
| `config.templateName` | `emergency_security_alert`. |
| `config.templateLanguage` | `en`. |
| `config.templateVersion` | `whatsapp-emergency-security-alert-v2`. |
| `config.optIn` | Consent evidence described below. |

Recommended non-secret `config` shape:

```json
{
  "wabaId": "<WABA_ID>",
  "templateName": "emergency_security_alert",
  "templateLanguage": "en",
  "templateVersion": "whatsapp-emergency-security-alert-v2",
  "testVideoUrl": "https://media.example.com/ketch/test-emergency-clip.mp4",
  "optIn": {
    "capturedAt": "<ISO_8601_TIMESTAMP>",
    "source": "OWNER_DASHBOARD",
    "policyVersion": "whatsapp-emergency-alerts-v1"
  }
}
```

The WABA ID and Phone Number ID are identifiers, not access credentials. The Cloud API access token and App Secret must remain only in the deployment secret manager. `testVideoUrl` is optional in production and is used only by explicit TEST deliveries; real ALERT deliveries ignore it and require a freshly generated secure evidence URL.

This `config` object is compatible with the existing schema: `notification_endpoints.config` is a `JSONB NOT NULL DEFAULT '{}'::jsonb` column whose `notification_endpoints_config_object_check` constraint requires a JSON object, which this shape satisfies. No new migration is needed, and future additive keys are ignored until the sender task reads them.

## Owner opt-in copy

Display an unchecked consent control before enabling the WhatsApp endpoint:

```text
I agree to receive time-sensitive WhatsApp emergency security alerts from Ketch Enterprise AI for my store. Messages may include the store, camera, incident type and detected time. I can disable WhatsApp alerts at any time in notification settings.
```

Store the consent timestamp, source and policy version in endpoint configuration. Enabling Telegram must not implicitly opt the owner into WhatsApp. Disabling the endpoint must stop new WhatsApp deliveries without deleting delivery history.

## Provider integration checklist

1. Keep the Meta Phone Number ID in `providerAccountRef`, the opted-in recipient in E.164 `destinationRef`, and the token only behind `credentialRef`.
2. Keep the approved template name, language and internal version pinned in endpoint configuration.
3. Configure `PUBLIC_API_BASE_URL` as public HTTPS and enable the secure evidence origin before turning on WhatsApp alert delivery.
4. Run the gated live smoke test with a verified recipient and public test video; it must send exactly one message clearly identified as a test.
5. Confirm a non-empty provider message ID and then remove the temporary smoke-test variables from the process environment.
6. Do not enable the production worker until the endpoint opt-in evidence and fallback ordering have been reviewed.

### Version 2 body

```text
A potential emergency was detected at {{1}}.

Camera: {{2}}
Detected: {{3}}
Event: {{4}}

Open this alert using the button below and follow your store's emergency procedure. This automated alert does not contact emergency services.
```

The button's dynamic value is the alert ID only; the fixed Ketch dashboard origin and route remain part of the Meta-approved URL. The sender renders the button as a `button` component with `sub_type=url`, `index=0` and one text parameter. The dashboard reads `alertId` and opens the matching alert-detail dialog immediately. This is an authenticated dashboard deep link, not an object-storage or camera URL.

Configure new endpoints atomically with:

```json
{
  "templateName": "emergency_security_alert",
  "templateLanguage": "en",
  "templateVersion": "whatsapp-emergency-security-alert-v2"
}
```

Existing version-1 delivery snapshots remain immutable for audit. Because Meta now expects the revised button component, do not retry an old version-1 snapshot as version 2 by mutating it in place; create new deliveries from the current endpoint contract instead.
